Refactor and redesign the existing planning module in this repository.

The goal is to replace the current planning implementation with a small, reliable, production-ready TypeScript design.

Do NOT blindly rewrite the repository. First trace the current planning flow and understand how it connects to Turn, TurnState, model gateway, tools, approval/permissions, progress tracking, execution, verification, and final response handling.

## Primary goals

1. Inspect the entire existing planning module and all of its callers.
2. Identify duplicated, unused, obsolete, defensive, brute-force, fallback, retry, counter, flag, and compatibility code.
3. Remove code that is no longer needed after the redesign.
4. Redesign planning around a simple typed contract.
5. Keep Turn as the ONLY owner of the overall agent loop.
6. Planning must NOT execute tools.
7. Planning must NOT contain its own loop.
8. Planning must NOT contain hidden retries or recursive planning.
9. Planning must NOT duplicate ProgressTracker responsibilities.
10. Preserve existing behavior outside planning unless it is clearly part of the broken/obsolete planning design.
11. Do not add unnecessary abstractions or framework-like architecture.
12. Use proper TypeScript types. Avoid `any`, unsafe casts, magic strings, and loosely typed objects.
13. Keep the implementation production-ready and easy to understand.

## Target architecture

Use this conceptual flow:

User
↓
Turn
↓
Observe
↓
Planning
↓
Approval (when required)
↓
Execution
↓
Verification
↓
Planning again only when genuinely required
↓
Final answer

Turn owns the lifecycle.

Planning only answers:

"What should be done next?"

Execution answers:

"How do I perform that action?"

Verification answers:

"Did it actually work?"

Progress/state answers:

"What has already happened?"

Do not mix these responsibilities.

## Target planning contract

Prefer a small model similar to this:

```ts
export type PlanStepType =
  | 'inspect'
  | 'edit'
  | 'run'
  | 'verify';

export type PlanStepStatus =
  | 'pending'
  | 'completed'
  | 'failed';

export interface PlanStep {
  readonly id: string;
  readonly description: string;
  readonly type: PlanStepType;
  status: PlanStepStatus;
}

export interface Plan {
  readonly id: string;
  readonly goal: string;
  readonly steps: readonly PlanStep[];
}
```

Adapt these types to the existing repository conventions instead of blindly copying them.

Planning should return a discriminated result:

```ts
export type PlanningResult =
  | {
      readonly kind: 'PLAN';
      readonly plan: Plan;
    }
  | {
      readonly kind: 'NO_PLAN';
      readonly reason: string;
    }
  | {
      readonly kind: 'CLARIFICATION';
      readonly reason: string;
    };
```

If the existing application needs different states, preserve the existing domain semantics but keep the result discriminated and strongly typed.

## Important planning rules

### Simple requests

Do not create unnecessary plans.

Example:

```text
User: "What does this function do?"
```

This should be able to proceed without constructing a multi-step implementation plan.

### Complex coding requests

Create a concise plan.

Example:

```text
Goal: Fix duplicate tool execution.

1. Inspect the turn/progress logic.
2. Identify why successful calls are repeated.
3. Apply the smallest safe fix.
4. Add or update the regression test.
5. Verify the behavior.
```

The plan should describe work, not individual tool invocations.

Do NOT generate plans like:

```text
read_file("src/foo.ts")
read_file("src/bar.ts")
edit_file(...)
run_command(...)
```

Those are execution decisions and belong to the executor/model.

## Planning must not become another agent loop

Do NOT implement:

```ts
while (...) {
  observe();
  askModel();
  execute();
  replan();
}
```

inside the planning module.

Planning should be a bounded operation:

```ts
const result = await planner.create(context);
```

Then return control to Turn.

If more information is needed, transition back through the normal Turn/Observe flow.

## Suggested interface

Use an interface along these lines if it fits the existing architecture:

```ts
export interface PlanningContext {
  readonly goal: string;
  readonly observations: readonly Observation[];
  readonly state: TurnState;
}

export interface Planner {
  create(context: PlanningContext): Promise<PlanningResult>;
}
```

Do not introduce unnecessary interfaces merely to follow this example.

Reuse existing repository types when they already represent the same concept.

## Plan lifecycle

The intended lifecycle should be:

```text
OBSERVING
   ↓
PLANNING
   ↓
AWAITING_APPROVAL
   ↓
EXECUTING
   ↓
VERIFYING
   ↓
COMPLETE
```

And when verification determines that additional work is genuinely necessary:

```text
VERIFYING
   ↓
PLANNING
   ↓
EXECUTING
```

Do not allow arbitrary phase transitions.

Planning should not directly transition itself through the entire lifecycle.

## Replanning

Replanning must be explicit.

Only replan when there is a real reason such as:

```ts
export type PlanningReason =
  | 'INITIAL'
  | 'NEW_INFORMATION'
  | 'VERIFICATION_FAILED'
  | 'BLOCKED';
```

Do not replan simply because a tool returned a normal result.

Do not use arbitrary counters such as:

```ts
if (attempts > 3) ...
if (planCount > 5) ...
if (retries > 10) ...
```

unless the repository already has a clearly justified global safety limit owned by Turn.

Do not use counters to compensate for incorrect state transitions.

* code that exists only to recover from another planning implementation

Do not remove something merely because it looks unused. Verify references first.

Use repository-wide search before deleting files/functions/types.

## Do not preserve dead architecture

If the old design contains multiple planning components such as:

```text
PlanningManager
PlanningController
PlanningLoop
PlanEngine
PlanProgress
PlanRecovery
PlanCoordinator
```

do not preserve them automatically.

Determine whether they have unique responsibilities.

If their responsibilities can be handled by a single Planner and TurnState, remove the redundant components.

The target should be approximately:

```text
planning/
  planner.ts
  plan-types.ts
```

or even fewer files if the existing repository is small enough.

Do not create files just for organizational appearance.

## State ownership

There must be ONE source of truth for plan state.

Prefer:

```ts
interface TurnState {
  phase: Phase;
  plan?: Plan;
  ...
}
```

rather than separate mutable state such as:

```ts
planner.currentPlan
planner.planStatus
planner.stepIndex
progressTracker.plan
turn.plan
```

Do not duplicate plan state across components.

If the existing TurnState already has a suitable representation, extend it rather than creating another state store.

## Step execution

Planning must not mark steps as completed merely because a tool was requested.

Bad:

```ts
step.status = 'completed';
await executeTool(...);
```

Completion should be based on the actual execution/verification result.

Prefer immutable state transitions where practical:

```ts
function completeStep(plan: Plan, stepId: string): Plan {
  return {
    ...plan,
    steps: plan.steps.map(step =>
      step.id === stepId
        ? { ...step, status: 'completed' }
        : step,
    ),
  };
}
```

Adapt this to existing state-management conventions.

## Model output validation

Do not trust raw model output.

If planning uses structured JSON, validate it at the boundary.

Reject:

* missing goal
* missing steps when a plan is required
* malformed step objects
* invalid step types
* invalid statuses
* duplicate step IDs
* empty descriptions
* unexpected structure

Prefer a small existing validation mechanism if the repository already has one.

Do not introduce a large validation framework for this.

## Prompt design

Keep the planner prompt small and deterministic.

The model should receive:

* user goal
* relevant observations
* relevant existing state
* constraints

It should NOT receive every tool schema if planning does not need them.

Use a prompt conceptually similar to:

```text
You are the planning phase of a coding agent.

Create a concise implementation plan for the user's request.

Rules:
- Do not execute tools.
- Do not invent files, APIs, or project behavior.
- Use only available observations.
- Keep the plan proportional to the task.
- Prefer the smallest safe change.
- Do not include tool calls.
- Separate implementation work from verification.
- Do not create a plan for simple informational requests.
- If required information is missing, request clarification.
- Do not modify files.
- Return only the requested structured result.
```

Adapt the prompt to the existing model gateway and message abstractions.

Do not duplicate system prompts already owned by the model layer.

## Turn integration

After the refactor, Turn should be understandable from one place.

The high-level logic should resemble:

```ts
switch (state.phase) {
  case 'OBSERVING':
    await observe(state);
    break;

  case 'PLANNING':
    await planning.create(state);
    break;

  case 'AWAITING_APPROVAL':
    await handleApproval(state);
    break;

  case 'EXECUTING':
    await executor.run(state);
    break;

  case 'VERIFYING':
    await verifier.run(state);
    break;

  case 'COMPLETE':
    return finish(state);
}
```

Do not introduce another loop inside any of these phases.

Adapt this to the repository's actual architecture.

## Error handling

Planning failures should have explicit typed outcomes.

Do not use:

```ts
catch {
  return false;
}
```

Do not silently fall back to execution when planning fails.

Do not swallow model/parser errors.

Use the repository's existing error/result conventions.

A malformed planner response should be distinguishable from:

* user clarification required
* planning blocked
* verification failure
* execution failure

## TypeScript quality

Do not add excessive generics or abstractions.

Prefer straightforward TypeScript.
